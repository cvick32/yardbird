#+TITLE: Recovering depth-five coverage on the remaining quantified VMT cases
#+DATE: 2026-11-11

* Scope
Start from the capture-preserving implementation measured in
application-captures-2026-11-11.org. Focus exclusively on the twelve inputs in the
original twenty-case quantified-transition-system sample that no measured Yardbird
configuration completed. The eight already-completing inputs are excluded.
Depth five means checks 0 through 4. Primary budget remains ten seconds plus one
second external grace, counting only depths completed within ten seconds. All
runs are sequential; profiles are separate diagnostic runs.

* Configuration experiments
On the unchanged capture-preserving binary, test batch100, batch20 with
--prefer-axioms, and --theory quantifiers (native arrays plus Yardbird quantifiers)
on all twelve. Existing saved batch20/guided results supply the baseline.

The 36-run screen recovers Lambda bakery.in.vmt with batch20 + prefer-axioms in
8.902 seconds, and flash_eager.in.vmt with batch100 in 9.357 seconds. The other ten
still fail. No tested single configuration recovers both. Larger batches are not
a general remedy: some inputs lose depth. Native arrays recover no full cases.
Repeated confirmation is recorded separately below.

* Concrete guidance gap
Countermodel transition lookup recognized universally quantified helpers but
stopped at existential action helpers. Generated VMT actions commonly have the
shape exists parameters . forall indices . update. A saved client/server trace
therefore ended at "no supported predecessor for array s_response_5f_received@1"
even though the source action contains its pointwise update/frame equation.

The change lets guarded equation tracing unfold existential parameters into their
source-defined witness terms. Each witness implication remains in the equation
path. A false implication is returned as the refinement frontier; an unknown one
is retained as unresolved. Only a satisfied implication allows traversal of its
body. Existing helper guards, active-branch selection, work budgets and frame
bounds remain in force. Arbitrary model equalities are never asserted.

EquationCompiler::for_trace enables this behavior only for guarded tracing.
Ordinary universal equation compilation and partial instantiation requests retain
their existing behavior. The change is in theories/quantifiers/equations.rs and
countermodel.rs; it adds no CLI option or trace enum variant.

* Validation

Tests reuse release dependencies with LTO disabled only for the test harness via
the recorded rustc wrapper. Benchmark executables use the normal release build

* Evidence for the remaining implementation targets
Before/after guided profiles use a five-second cooperative budget and ten seconds
of external grace to allow diagnostic serialization and long refinement steps to
finish. Only progress within five seconds is counted. One preliminary client trace
with one-second grace was externally killed before it could emit its profile; its
progress record is retained. The longer diagnostic grace is not a performance win.

1. Scalar predecessor constraints and guarded frame equations (German, Chandra).
   After the patch, German's terminal scalar observations include s_MemData@1,
   s_AuxData@1 and s_Exgntd@1; Chandra's include s_a@1. Scalar leaves are currently
   TraceStatus::Value in countermodel.rs, with no traversal of their defining
   action constraints. Transition equations under guarded forall bodies are
   another missing path: EquationCompiler walks conjunctions and equations but
   does not carry conditions through =>. Chandra still has unsupported reads of
   s_d@1, s_e@1 and s_m@1. Add guarded scalar/pointwise predecessor support while
   retaining all action and quantifier guards. This is the first recommended
   implementation target; its performance effect has not yet been tested.

2. Correlated existential-property witnesses (client/server).
   Before the patch the trace repeatedly stops at no supported predecessor for
   s_response_5f_received@1 and guided search selects zero instances in its
   five-second profile. Afterward the update is explained, seven guided instances
   are selected, and three checks complete. The residual is the opaque existential
   helper __yardbird_quantifier_80: connect the received response's node/response
   to the request witness exposed by the earlier respond action. Reusing proved
   properties and exact binding alone do not supply that connection.

3. Boolean static-relation frontiers (multisig, database replication).
   After the patch, unsupported predecessor reads disappear from both sampled
   traces. Multisig's remaining frontier is s_sig_auth@0; database replication's
   are s_op_in_tx@0 and s_op_node@0 (encoded symbol spellings retained in JSON).
   These are InitialState read frontiers. The relational matcher currently admits
   Unsupported frontiers only, so it does not attempt its source-clause joins at
   these Boolean reads. A focused next experiment is admitting those frontiers to
   existing guarded matching, preserving full model validation. InitialState is
   not itself evidence that a relation should be true or false.

4. Later-frame stalls (distributed lock, toy consensus, sense barrier,
   Szymanski, Chord).
   The near-miss controls above show persistent stalls after otherwise quick
   prefixes. These should be traced at the first unfinished check, with attention
   to guards and correlated tuples, after the earlier representation gaps are
   addressed. Szymanski and Chord still need equally focused late-frame traces;
   a specific missing lemma has not been established for them.

These are source-backed hypotheses and explicit frontiers, not claims that the
remaining cases have been solved. The usual native-quantifier bypass was excluded:
all experiments keep quantified reasoning in Yardbird.

* Trace and run evidence
The after-change profile selects 23 guided instances on multisig versus three
before, and reaches two checks versus one. Database replication selects eight
versus six but remains at one check in the five-second profiles; the ten-second
screen exposes its depth regression. No EvaluationFailed or InconsistentStep
statuses occur in these before/after profiles.

The twelve initial batch20 profiles show less than three percent of process wall
time inside raw solver checks. Chandra completes only fourteen solver checks in
its five-second profile, so it also has high per-refinement overhead; that does
not establish a particular caching optimization as the right next fix.
