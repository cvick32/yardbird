#+TITLE: Default preservation of quantified-helper application captures
#+DATE: 2026-11-11

* Change
Preserve the exact capture arguments of each admitted quantified-helper
application. Only quantified variables are chosen by the existing domain matching
and term-selection machinery. Distinct applications remain distinct when their
capture arguments have equal values in the current model. Include nested helper
applications in derived instances as well as original source applications.

Explicit request bindings remain literal. A partially specified capture request
must agree syntactically with an actual application; a fully specified request
may introduce a new application. Existential witness functions receive the same
captures as their helper. Application expansion is paged and bounded, with queues
reset when the graph/model changes. Complete grounded candidates are independently
validated; model equalities are search hints, never asserted lemmas.

The former --guided-source-captures switch is a compatibility no-op. This behavior
now applies to default, batch and guided quantifier search alike.

* Experiment
Use exactly the previous 20 generated VMT inputs, five from each of mypyvy,
Cubicle, Lambda/MCMT and IvyBench, under examples/quantified-transition-systems/.
Base revision cad045235f613ef05a7239ee01e4d8e2da670320. Compare the changed binary
against saved main results and saved native-Z3 results. No unrelated benchmarks
and no native-quantifier bypass configurations are included in the rerun.

Depth 5 (checks 0 through 4); 10-second cooperative timeout plus one-second external
grace; sequential, unprofiled release runs. Only depths completed within the
10-second budget count. These are bounded checks, not unbounded proofs. The
sample is purposive and family-balanced, not a random estimate of the full corpus.

Raw outputs, scripts, exact commands, build/test logs, source hashes and the diff
are retained locally under benchmark_results/application-captures/ (gitignored).
Baseline evidence: notes/quantified-search/main-sample20-2026-11-10.org and .json.

Six new regression tests cover model-equivalent but syntactically distinct
applications, nested derived applications, partial literal requests, fully bound
new applications, total occurrence budgets, existential witness arguments, and
graph-growth invalidation. Existing grounding coverage checks preserved capture
choices and term-selection observations.

cargo fmt --all -- --check and git diff --check pass. Strict Clippy (lib + tests)
reports eight pre-existing warnings in quantifier ground/read_support and CLI

Batch20 and guided each recover mypyvy lockserv, Cubicle bakery, and IvyBench

on seven and loses on one (Lambda bakery: four depths to two). Default gains depth

on six and loses on one, recovering MESI and ticket as full completions.

There are no errors, counterexamples or unexpected semantic outcomes in the 80-run
screen. A reported depth_limit alone is insufficient: only depth completions within
the budget count. Ticket/full-stack finishes its final depth within the budget,
although total process wall time including output is 10.657 seconds.

The change improves the batched and guided configurations, but does not beat Z3
overall and is not a uniform performance improvement. No changed configuration
completes more depths than Z3 on any input in this sample. Peterson is the clear
speed win; the tiny apparent Bakery timing win is a tie at this measurement scale.

Guided Peterson is 4.54x faster than the saved Z3 median and 1.65x faster than the old guided median.
Bakery moves from a ten-second timeout to 0.316 seconds, matching Z3. The lock
servers complete reliably but remain much slower than Z3; IvyBench batch20 at

Three additional default MESI repetitions all time out with two depths completed.
The old default screen completed it in 4.133 seconds. New batch20 and guidance
complete it in about 0.42 seconds. This regression must remain visible when
considering a default configuration; increasing the winner budget is a separate
policy choice, not silently included in this capture-preservation change.

* Diagnostic profiles and next targets
Nine separate five-second profiled runs cover lockserv, Cubicle bakery and MESI
under default, batch20 and guided. They are diagnostic, not timing confirmations.
Every run records application_capture_groundings, confirming the new path is active.
Nested timers below must not be summed as independent costs.

On default MESI, 5.084 seconds of wall time contains 4.663 seconds in strategy_sat
and only 0.027 seconds in raw solver checks. It completes two depths after 68 checks
and 108 installed instances. Binder preparation costs 0.722 seconds, representative
extraction 0.826 seconds and dependency discovery 0.430 seconds. The old profiled
default completed all five depths in 68 checks and 209 installed instances; the
new batch20 completes all five in 19 checks and 107 instances. Most productive
batches contain one instance, though occasional multi-instance batches matter.

Default Bakery similarly spends 4.597 of 5.139 seconds in refinement and only
0.060 seconds in raw checks; batch20/guided finish in 14 checks and 66 instances.
Lockserv batch20 and guided use the same 59 checks and 431 instances, but guidance
spends 1.316 seconds discovering dependencies versus batch20's 0.356 seconds.

The next implementation targets are whole-instance selection/batching and temporal
relevance among actual helper occurrences, followed by avoiding repeated graph,
extractor and dependency work. These are inferences from the batch-size ablation
and profiles, not a claim that a specific new ranking heuristic has been tested.
Preserving captures fixes the chosen context; it does not choose which actual
context or quantified-variable instance should be installed next.

* Reproduction and artifacts
128 new runs total: 80 primary, 36 timing confirmations, three default MESI
confirmations, and nine profiles. All are Yardbird runs on the quantified-transition-
system subset; no Z3 reruns or native-quantifier bypasses were added.

Run benchmark_results/application-captures/run-benchmarks.sh after building with
benchmark_results/application-captures/cargo.sh build --release --locked --offline
--bin yardbird. The compare.py script checks input hashes and experimental budgets
against the saved baseline. run-followups.sh records regression checks and profiles;
confirmation metadata retains all commands for the six-case repetitions.

Compact evidence is application-captures-2026-11-11.json beside this note. The full
raw experiment directory also retains exact commands, solver outputs, progress
files, metadata, code hashes, tracked.patch, the new application_captures.rs source,
compiler logs and comparison.csv. The source and experiment remain uncommitted.
